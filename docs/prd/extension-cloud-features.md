# PRD: Extension Cloud Features

**Product:** Trail extension ↔ cloud account  
**Scope:** Extension-side auth, account linking, token exchange, and future sync/sessions  
**Status:** Living doc

---

## 1. Goals & Success

- **Primary:** User can link the browser extension to a Trail account (app.gettrail.net) and receive a signed token for API access.
- **Secondary:** Clear flow when unlinked (prompt to sign in); no silent failures; secure code exchange.
- **Future:** Sync trees/settings to cloud; list sessions/devices; revoke tokens.

---

## 2. User Flows

### 2.1 Extension: User not linked → Start link flow

1. User opens sidepanel; account state is “signed out” or “no token”.
2. UI shows “Sign in to Trail” (or similar); CTA **“Sign in”** / **“Connect account”**.
3. Extension calls backend to **start auth portal**: POST (account app or API) with `source=extension`, `locale`, `returnUrl`.
4. Backend creates portal session (id, url, expiresAt, pollIntervalMs); returns url.
5. Extension opens `portalSession.url` in a new tab (e.g. `chrome.tabs.create`).
6. User lands on account app (or Better Auth) and signs in; after auth, account app shows “Connected” or redirects to extension page with code.
7. Extension **polls** `checkAuthPortal(portalSession.id)` until:
   - **approved:** backend returns snapshot (or extension fetches snapshot); extension stores token from snapshot or from exchange step.
   - **expired:** extension shows “Sign-in link expired. Please try again.”; user can start again.
8. If approved and snapshot contains token: extension persists token (e.g. chrome.storage.local). If snapshot contains code: extension must exchange code for token (see 2.2).

### 2.2 Extension: Exchange code for token (alternative flow)

1. User has signed in on app.gettrail.net and is on **/extension** with `?code=...` (code generated by account app and shown to user to type, or passed via redirect).
2. Extension (or user) supplies this code to backend. Extension calls **exchange** endpoint (account app: POST /api/extension/exchange) with body `{ code }`.
3. Backend validates code (with API or DB): exists, not used, not expired. Marks code used (usedAt).
4. Backend creates JWT (createExtensionAccessToken(userId)), returns `{ token, expiresAt }`.
5. Extension stores token; uses it for authenticated API requests (e.g. sync, profile).
6. **If code invalid/expired:** Backend returns 4xx; extension shows error and asks user to get a new code from app.

### 2.3 Extension: Already linked

1. On load, extension reads stored token; optionally validates (e.g. call API me or health with Authorization).
2. If valid: account UI shows “Signed in” / email or name; no prompt to sign in.
3. If invalid/expired: clear token; show “Sign in” again (flow 2.1 or 2.2).

### 2.4 Account app: Generate code for extension

1. User on app.gettrail.net/extension (signed in).
2. If no `?code=` in URL: account app can show “Enter code in extension” and generate a one-time code (POST internal API → createExtensionLoginCode(userId)).
3. Account app displays code (and optionally redirects to `/extension?code=<code>` so user can copy or so extension can open that URL and read code from query).
4. User types code in extension (or extension opens URL and parses code) → exchange (2.2).

### 2.5 Revoke / sign out (extension)

1. User clicks “Sign out” in extension.
2. Extension deletes stored token; does not call backend to revoke (JWT remains valid until exp). Optional future: revoke endpoint to invalidate token server-side.
3. UI returns to “Sign in” state.

## 3. Edge Cases & Handling

| Scenario | Handling |
|----------|----------|
| **Portal URL open but user never completes auth** | Polling hits deadline (expiresAt); extension shows “Sign-in link expired.”; user can start again. |
| **User closes extension tab during polling** | flowRef/cancel: on unmount or cancel, stop polling; no stale state. |
| **Network error during startAuthPortal or checkAuthPortal** | Normalize to AccountError (e.g. network); show error in UI; allow retry. |
| **Backend returns approved but no snapshot/token** | Extension can call getAccountSnapshot() after approval to fetch token/snapshot. |
| **Exchange: code already used** | API returns 4xx; extension shows “Code already used”; user must get new code from app. |
| **Exchange: code expired** | Same as above; clear message “Code expired”. |
| **Token expired while using extension** | API returns 401; extension clears token and shows “Sign in” again. |
| **Multiple tabs/windows:** same extension, same token | Token in chrome.storage.local is shared; all tabs see same account state. |
| **User signs in on different Better Auth identity** | New userId; new code/token; old token (old userId) still valid until exp. No automatic revoke of old token. |
| **Internal API (login-code) unavailable** | Account app cannot create code; show error on /extension; extension cannot complete code flow. |
| **CORS / extension origin** | Exchange and portal endpoints must allow extension origin or be called from account app only (exchange from extension may use fetch to account app with credentials/cookie if same domain, or proxy). Document: if extension calls account app directly, account app must allow extension’s origin. |

## 4. Technical Constraints

- **Extension:** Chrome/Brave (Chromium); messaging via chrome.runtime; storage chrome.storage.local for token. No cookie access to app.gettrail.net unless same-site.
- **Auth portal:** Implemented on account app (or API); returns URL that leads to Better Auth login then back to account app; portal session stored server-side with short TTL (e.g. 5–10 min).
- **Login codes:** Stored in DB (ExtensionLoginCode); unique code; userId; expiresAt; usedAt. Created via internal API (account → API). Single use.
- **JWT:** HS256; secret in env (TRAIL_EXTENSION_JWT_SECRET); payload sub=userId, iat, exp. TTL e.g. 30 days. Extension does not decode; sends as Bearer.
- **API:** Protected routes require Authorization: Bearer <token>; verifyExtensionAccessToken on API or account app. API does not create tokens; account app creates and returns token after exchange.
- **Internal API:** Account app calls api.gettrail.net with internal key (header); only login-code creation and user ensure; not exposed to browser.
- **No refresh token:** Token expiry forces re-auth (portal or code exchange). Optional future: refresh token or longer-lived token.

---

## 5. Future: Sync & Sessions

- **Sync:** Extension sends tree/settings to API when linked; API stores per userId. Dashboard reads from API. Extension pulls last state on load when online.
- **Sessions:** API records “sessions” (device id, last seen, user agent); dashboard /extension page lists them; user can revoke.
- **Revoke token:** API or account app endpoint to blacklist token or delete session; extension loses access on next 401.

---

## 6. Out of Scope (current)

- Refresh token flow.
- Multiple devices list and revoke in UI.
- Sync of trees to cloud (extension is local-only).
- Extension calling API for anything beyond auth (no sync API yet).
